# Cranelift C4 — scalar integer lowering

C4 extends the verified C3 FIR-to-CLIF boundary across the scalar integer operations whose semantics are already closed by FIR. It is split historically into C4a and C4b, but the integrated milestone is reviewed and merged as one unit.

## Supported operations

C4 lowers:

- wrapping and checked integer `add`, `sub`, and `mul`;
- signed/unsigned `div` and `rem` with checked FIR semantics;
- bitwise `and`, `xor`, and `or`;
- checked left/right shifts, with signedness selecting arithmetic versus logical right shift;
- integer bitwise not;
- exact-identity and provably lossless integer widening through sign-extension or zero-extension;
- all C3 comparisons, branches, scalar constants, parameter loads, and scalar returns.

The supported integer representations are `byte`, `u8/i8`, `u16/i16`, `u32/i32`, `u64/i64`, and pointer-sized integers for the active target layout.

## Semantic boundary invariants

CLIF representation equality is never sufficient to establish Forge type equality. Before lowering, C4 requires:

- a parameter load result to have exactly the local's FIR type;
- integer unary results to retain the operand FIR type;
- binary operands to have identical FIR types;
- comparison results to be exactly FIR `bool`;
- non-comparison integer binary results to exactly match the operand FIR type;
- conversion result type to exactly match the explicit FIR target;
- branch and return typing to remain valid under the FIR verifier.

This prevents equal-width types such as `bool`, `u8`, and `i8` from becoming interchangeable at the backend boundary.

## Integer conversions

`FirInstructionKind::Convert` currently records the source value and target type, but no truncation/range-check policy. C4 therefore lowers only conversions that are unambiguous without inventing language semantics:

- exact identity is a no-op;
- signed to wider signed uses sign extension;
- unsigned to wider unsigned uses zero extension;
- unsigned to a wider signed type uses zero extension when the wider signed domain contains every source value.

Narrowing, same-width signedness changes, and signed-to-unsigned conversions are rejected explicitly until FIR records the required lossy-conversion semantics. C4 does not silently define these operations as truncation or reinterpretation.

## Control-flow contract

`FirBlockId` remains the identity/index used by verified FIR. Lowering must nevertheless not depend on block IDs also being dependency order. C4 therefore schedules a cloned, already-verified function for lowering: the entry block is first, then blocks whose scalar input values are available. The original verified FIR is not mutated.

Acyclic dominating cross-block scalar values are supported. Cyclic or merge dependencies requiring CLIF block arguments/phi construction remain outside C4 and return `UnsupportedControlFlow` explicitly.

## Overflow and trap behavior

- wrapping add/sub/mul use ordinary CLIF integer operations;
- checked add/sub/mul use Cranelift overflow-producing operations and trap on the overflow flag;
- checked shifts explicitly trap when the shift count is greater than or equal to the operand width;
- signedness selects signed versus unsigned division, remainder, comparisons, extension, and right shift;
- bitwise operations must not carry FIR overflow metadata.

Runtime integer negation is deliberately **not** lowered in C4. Forge constant evaluation uses checked negation, and the frontend already computes a per-function checked/wrapping overflow policy, but `FirInstructionKind::Unary` does not currently carry that policy. Lowering it as plain CLIF `ineg` would silently choose wrapping behavior. C4 therefore rejects negation until FIR makes the overflow semantics explicit.

C4 does not reinterpret malformed overflow metadata or silently select wrapping behavior.

## Deliberate boundaries

C4 still does not lower integer negation without FIR overflow metadata, lossy integer conversions without a FIR conversion policy, mutable locals/stores, floating point, aggregates, calls, globals, closures, `select`, or SSA merge values. Those remain explicit unsupported boundaries for later milestones.

## Merge gate

C4 is mergeable only when:

1. all C0–C3 regression tests remain green;
2. both AArch64 and RV64 verify generated CLIF;
3. wrapping and checked arithmetic are covered across integer widths and signedness;
4. signed/unsigned division, remainder, shifts, comparisons, and lossless conversions are distinguished correctly;
5. ambiguous integer negation and lossy conversions are rejected instead of assigned backend-local semantics;
6. equal-width but semantically different FIR types are rejected at loads, unary/binary results, and comparisons;
7. a valid CFG whose dependency order differs from block-ID order lowers correctly;
8. strict repository CI passes formatting, locked build, snapshots, frontend/workspace tests, conformance, and Clippy.
