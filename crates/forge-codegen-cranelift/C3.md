# Cranelift C3 — basic FIR control-flow lowering

C3 is the first milestone that lowers non-empty verified FIR functions to CLIF. It does not move Forge language semantics into Cranelift: AST/HIR/type-checking decisions remain above the frozen `forge-fir` boundary.

## Supported surface

C3 lowers scalar function signatures already representable by C2 and these FIR operations:

- integer and boolean constants;
- loads of immutable function parameters;
- integer equality/inequality and ordered comparisons;
- `goto`, boolean `branch`, and scalar/void `return` terminators;
- multiple functions in one FIR module;
- AArch64 and RV64 CLIF verification.

Signedness is taken from the FIR operand type. Comparison results are required to be FIR `bool`; identical CLIF widths are never sufficient to substitute a different Forge type.

## Control-flow contract

`FirBlockId` is an index into `FirFunction.blocks`, matching the current FIR lowerer and verifier contract. C3 preserves that identity instead of treating the block vector as freely reorderable storage.

Scalar values may cross block boundaries when ordinary SSA dominance makes that legal. C3 tracks already-lowered scalar definitions across blocks and the final Cranelift verifier remains mandatory to reject invalid dominance or malformed CLIF. Cyclic or merge dependencies that require CLIF block arguments / phi construction are explicitly outside C3 and return `UnsupportedControlFlow`.

## Deliberate C3 boundaries

C3 does **not** lower mutable/non-parameter locals, stores, arithmetic, conversions, calls, globals, closures, aggregates, `select`, `unreachable`, or runtime/global initializers. Those remain explicit errors rather than implicit fallbacks.

The backend also checks exact FIR type identity at semantic boundaries where machine representations can coincide: parameter loads, comparison operands/results, branch conditions, and return values. This prevents `u8`, `i8`, and `bool` from becoming interchangeable merely because each currently lowers to CLIF `i8`.

## Validation requirements

Before C3 is mergeable:

1. the C2 type-lowering suite must remain intact;
2. the basic branch example must verify on AArch64 and RV64;
3. signed and unsigned comparison condition codes must differ correctly;
4. a dominating scalar value must survive across multiple FIR basic blocks;
5. all generated functions must pass Cranelift verification;
6. the repository's strict read-only CI must pass with the locked workspace, generated snapshot, frontend/workspace tests, conformance suite, formatting, and Clippy.
